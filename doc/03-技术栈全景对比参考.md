# BeAtBench — 技术栈全景对比参考（决策支持）

> 用途：回答「并不一定要 Qt+PortAudio 这一套」——把候选栈全部摆上台面做优缺点对比。
> 本文件独立于 [02-对齐稿](./02-C++Qt方案对比与切音工作流.md) 的既定结论，供你复核选型。
> 评分是带权重的**主观判断**，权重与假设均已标注，可随你的实际情况调整。
> 项目许可：**GPL-3.0**。

---

## 1. 结论先行

1. **在你「会 C++」的假设下，C++/Qt 在 v1 口径与长期口径均排第一**；唯一有实力翻盘的对手是 **Rust + egui**——如果你会（或愿意投入学）Rust，它反超（见 §4）。
2. **PortAudio 与 v1 无关**（v1 无实时播放/试玩）——它从来不是「选 Qt 的理由」，而是 Phase B 的长期理由；音频后端可跨栈互换（§5）。
3. 第二梯队：C#/Avalonia、C++/Dear ImGui。第三梯队：Tauri+TS、Java、Electron、Godot——各有人试过 BMS 编辑器（§6），但短板明显。

## 3. 候选栈逐一分析

### A. C++20 + Qt 6.8 LTS Widgets（+ 后期 PortAudio）★ 当前主推

- **先例**：BmsTWO（Qt6，GPL-3.0，同赛道直接参照）、imbms（C++）、BMSE/iBMSC 谱系。
- **优点**：编辑器控件全（表格/树/Dock/撤销框架/多窗口）；QPainter 自绘自由；BMS 编辑器 20 年主线栈；C++ 性能无短板；Qt LGPLv3 动态链接合规；跨平台成熟。
- **缺点**：C++ 无 GC/边界检查（靠纪律 + sanitizer）；Qt 部署体积 30-50MB；LGPL 动态链接义务；Web 化基本无路（Qt WASM 体验一般）。

### B. Rust + egui/eframe（+ cpal/kira）

- **先例**：Phira（Rust 音游编辑器+试玩一体，GPL-3.0）、phichain（LGPL-3.0）；portaudio-rs 绑 PortAudio 也可。
- **优点**：内存安全 + 强类型 = 单人长线项目最省心；单二进制分发（几 MB~十几 MB）；依赖全 MIT/Apache，GPL 最干净；egui/eframe 原生支持 wasm（未来 Web 版有路）；cpal/kira 低延迟音频生态成熟。
- **缺点**：egui 编辑器生态弱于 Qt（Dock/表格/富文本要自研或找社区件）；即时模式每帧重绘，数万 note 渲染要自己做缓存策略；**需要你投入 Rust 学习成本**（最大变量）。

### C. C# + .NET 8 + Avalonia 11（+ NAudio；osu.Framework 变体）

- **先例**：Quaver（C# MonoGame 编辑器，MPL-2.0）、osu!lazer BMS ruleset（播放向，编辑器支持弱）。
- **优点**：语言友好、开发效率高；Avalonia 跨平台 + XAML 成熟；NAudio 波形/试听够用；GC 免去大部分内存管理。
- **缺点**：**ASIO 低延迟路径最弱**（ManagedBass 专有须避开，NAudio 只有共享模式）；自包含分发 60-100MB；高密度编辑器先例少（osu.Framework 的编辑器是 osu! 特化的，复用面小）。

### D. C++ + Dear ImGui + SDL/GLFW（+ RtAudio/miniaudio）

- **先例**：游戏工具界通用（无 BMS 编辑器先例，但 ImGui 写编辑器有大量参考）。
- **优点**：即时模式开发极快、性能好；分发轻；miniaudio/RtAudio 直接绑定。
- **缺点**：**复杂编辑器 UI（多面板/表格/富文本/输入法）是 ImGui 的传统弱项**；Dock/表格/文本输入全要自己垒；中文 IME 处理麻烦。适合「游戏内小工具」，不太适合「专业谱面编辑器」。

### E. Tauri 2 + TypeScript（React/Solid）+ Rust 侧 cpal

- **先例**：MikuroXina/bemake（bms-rs 作者的 BMS 编辑器尝试，Apache-2.0）、Sonolus（Web 编辑）、OpenChart-web（多格式 web 编辑器）。
- **优点**：Web 技术栈迭代最快；UI 生态最丰富；Tauri 壳轻量；Sonolus 证明网页能做出好谱面编辑器。
- **缺点**：编辑器型高密度 UI 在 Web 要大量自研（虚拟滚动/画布）；**音频精确调度是历史难题**（WebAudio 共享级延迟 ~10-20ms，无 ASIO）；前后端桥接样板多。适合「网页版优先」的战略，不适合桌面体验优先。

### F. Java + JavaFX / libGDX（beatoraja 生态）

- **先例**：beatoraja（libGDX 播放器，GPL-3.0）。
- **优点**：beatoraja 同生态，jportaudio 现成（ASIO 可用）；JavaFX 控件可用；跨平台。
- **缺点**：桌面编辑器先例少；JVM 分发与启动体验一般；libGDX 的 UI（Scene2D）不适合高密度编辑器，JavaFX 又割裂于游戏生态。适合「给 beatoraja 做伴生编辑器」的战略，不适合独立产品。

### G. Godot 4

- **优点**：内置音频/渲染/UI 一站式；MIT；跨平台。
- **缺点**：编辑器型 UI（多面板/表格/文本）最弱；无 ASIO；桌面原生感差。适合做游戏，不适合做专业编辑器。

### H. Electron + TypeScript

- **先例**：bemuse 是 Web 播放器（AGPL 不能抄），无编辑器先例。
- **优点**：同 E 的 Web 生态。
- **缺点**：同 E 的音频短板 + 体积 ~100MB + 内存占用高；比 Tauri 无任何优势。**直接淘汰**。

> 未列：Flutter desktop（文本/表格编辑器生态弱）、Unity（编辑器型应用无先例、体积大）。

## 5. 音频后端与 UI 栈是两件事（可拆可换）

- PortAudio 有 C（原生）、Rust（portaudio-rs）、Java（jportaudio，beatoraja 在用）、C#（P/Invoke）绑定 → 换 UI 栈不必换音频栈。
- **ASIO 独占低延迟**只有桌面原生栈能充分兑现：C++/Rust/Java 强；C# 弱（NAudio 共享模式，ManagedBass 专有避开）；Web 无。
- 结论：无论最终选什么，`AudioBackend` 抽象层（02 对齐稿 §5.1）都能保住投资。

## 7. 决策检查清单（5 问定栈）

1. **你 Rust 熟练吗/愿意学吗？** 是 → B 反超 A，认真考虑 Rust/egui；否 → 维持 C++/Qt。
2. **Qt Widgets 有经验吗？** 无 → 有学习成本，但 Qt 文档/生态是桌面 UI 里最好的，可控。
3. **ASIO 级低延迟试玩是硬需求吗？** 是 → C++/Rust 最稳（PortAudio/cpal），C# 最弱；否 → 音频约束几乎消失，选型只看 UI。
4. **在意安装包体积吗？** C++ 最轻（~几 MB+Qt 库），.NET/Electron 60-100MB。
5. **未来想要 Web 版吗？** 是 → 核心层用 C 接口或选 Rust（wasm 直通）；Qt 上 Web 基本无路（Qt WASM 体验一般）。

## 9. 我的建议（供复核）

**维持 C++/Qt/PortAudio 决策**，理由按你的实际情况排序：
1. 你会 C++（熟悉度是 solo 项目最大权重）；
2. BMS 编辑器主线 20 年都在 C++/Qt，BmsTWO 是现成的同栈参照物；
3. 长期要试玩/切音 → PortAudio=beatoraja 同款 ASIO 路径，是这条路上最稳的音频方案；
4. 跨平台空间保留（Windows 优先不影响架构）。

**但记住两点**：① PortAudio 与 v1 无关，v1 的价值全在 UI/模型/解析，别在音频上提前投入；② 换栈成本最低的时刻是现在——如果你看完觉得 Rust 才是归宿，趁 M0 之前换，模型与 codec 设计（02 对齐稿 §4）在两个栈下完全通用。
