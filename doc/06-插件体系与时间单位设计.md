# BeAtBench 插件体系与时间单位设计（06）

> 本文件回答两个架构问题：
> 1. **插件/扩展预留怎么搭**（CLI 作为「非 API 接口」的定位与分层）；
> 2. **时间单位统一在哪里**（小节拍子 ↔ 时间轴 ↔ 采样率的换算边界，1/3 拍无损）。
> 配套：协议规范见 §3（命令 JSON 协议已随 M1 落地，本文是它的正式规格）。

---

## 1. 插件体系：三层接口漏斗

用户设想：CLI 不只是批处理工具，还是将来插件/扩展的「非 API 接口」。
我们把它落成**三层接口漏斗**——同一能力从里到外三层口径，不搞两套逻辑：

```
┌─────────────────────────────────────────────────────────┐
│ 第 1 层  进程内 C++ API（core 头文件）                     │
│         核心组件/编辑器内部组件直接调用，最深集成           │
├─────────────────────────────────────────────────────────┤
│ 第 2 层  JSON 命令协议（本层 = 唯一操作面，doc/02 §6.1）    │
│         Command 注册表 + 信封分发（dispatch）              │
│         GUI = 协议客户端（进程内调用）                     │
│         CLI --json = 同一协议的进程外入口                  │
├─────────────────────────────────────────────────────────┤
│ 第 3 层  外部插件进程（将来，M8+ 或按需）                   │
│         独立进程 + 插件清单（plugin.json）+ 协议收发        │
│         语言无关（Python/JS 生态）、崩溃隔离、热更新        │
└─────────────────────────────────────────────────────────┘
```

设计要点：

- **注册表是唯一入口**：所有能力（内建或插件）以平等身份注册。
  `CommandRegistry`（M1 已落地）只是第一个；规划中的还有 `CodecRegistry`
  （格式 → reader/writer/timing 模型，**换格式 = 换映射表**的核心兑现点）。
  core 只认接口，不认识任何具体插件。
- **GUI 也是协议客户端**：M2 的界面层不直接翻模型结构体，而是调
  `global_registry().dispatch(...)`——和外部进程走完全相同的信封。
  好处：GUI 只是引擎的另一个客户端；插件加的命令 GUI 天然可用，
  不需要为 GUI 单独开 API 面（避免「两套逻辑」漂移）。
- **CLI --json 是协议在进程边界上的投影**：stdin/stdout 传信封，
  退出码只回答「信封产没产出」，语义永远看信封 `ok` 字段（doc/06 §3.4）。
  脚本/CI/Web 后端/外部工具都走它，不需要链接 core。
- **协议版本化**：`version` 命令返回 `api` 版本号（`kApiVersion`），
  语义不兼容变更时 +1；`capabilities` 命令宣告能力（命令清单 + 格式清单），
  客户端启动时先问一遍再干活——这就是外部插件发现内建能力的握手。
- **安全/权限（将来）**：插件清单声明所需能力（读谱/写文件/执行命令），
  GUI 审批后放行；命令是权限的最小粒度。M1 不做，架构上留好：所有入口
  都经过 dispatch 这一道，将来加闸只有一处。
- **避坑原则**：不为插件在 core 里开旁路（如直接暴露内部结构指针给插件）；
  插件只能通过注册表接口交互。core 保持零依赖（JSON 都是自写的），
  插件不会破坏「core 可独立编译测试」这条基线。

**M1 已落地的钩子**：`Registry` + 内建五命令 + `--json` 入口 + `api` 版本 +
`capabilities`。**M2 预告**：GUI 经 `global_registry().dispatch` 复用同一批命令。
**M3 已落地（2026-08）**：`CodecRegistry`（`core/codec/`）——格式 → reader/writer/模式，
`capabilities.formats` 改为动态声明（当前 `["bms"]`），`info/check/convert` 的读写
统一走注册表（format 参数/扩展名 → codec）；`Chart.mode_id` 记录游玩模式
（bms：sp7k/dp/battle/pms9k，读时按 #PLAYER/扩展名推断）。
**将来**：`PluginLoader` + `plugin.json` 清单、外部进程适配器（把 dispatch 接到子进程管道上）。

## 2. 时间单位：换算边界与 1/3 拍无损

### 2.1 问题

- BMS 以**小节拍子**为时间单位（`(measure, pos)`，pos 为有理数）；
- 有的音游以**时间轴**（秒/毫秒/采样帧）为单位；
- 播放/导出最终一律落回**采样频率**。
- 疑虑：`1/3`、`1/6` 拍（BMS 一行奇数组采样，如 `#00111:0102000300`）
  若先换算成时间，就**无法 100% 精确换算回来**。

### 2.2 决策：身份坐标与换算边界分离

```
谱面身份坐标（唯一，永不变换）
  音乐坐标 (measure: int64, pos: Rational)        ← 事件的唯一标识
        │
        │ 只此一处换算（双向、有理数精确）
        ▼
  TimingEngine（每格式一个实现，BMS 版 M1 已落地）
  time_us(m, pos) / position_at(us)                ← 含 BPM 分段积分与 STOP 间隙
        │
        │ 只在此边界出现，单向
        ▼
  采样帧 frame = round(time_us × rate / 1e6)       ← 播放/导出/渲染，不入模型
```

1. **身份永远是音乐坐标**：`Event<T>.pos` 是事件唯一的标识性坐标，
   存的就是 (measure, Rational)。**任何地方都不存「先换算好的时间」作为身份**。
   → 这就是 1/3 拍无损的答案：正因为从不先转时间，往返写回时
   `Rational(1,3)` 原样回到槽位 `#…3`（LCM 槽位重建，M1 已实现），
   时间换算 `1/3 拍 = 拍数 × 60/BPM ÷ 3` 也是精确有理数。
2. **换算只有一处**：`TimingEngine`。双向（音乐→墙钟、墙钟→音乐，
   落在 STOP 间隙内的时间逆映射回 STOP 起点），内部 double 秒 + 边界
   int64 微秒（llround）。**时间永远是由身份坐标派生的只读缓存**，
   随 BPM/STOP/节拍事件变化重建（M1 全量重建，GUI 阶段改脏区增量）。
3. **采样率只在渲染边界出现**：播放/导出时 `frame = round(us × rate / 1e6)`，
   单向、不入模型。不同格式可以有不同的量化策略（BMS 写回按槽位、
   WAV 导出按采样帧），互不干扰。
4. **时间轴格式（osu! 等）怎么进**：codec 读取时按其自带 timing 模型
   （timing points → BPM 分段）把原生坐标换算成规范音乐坐标 (measure, pos)；
   写回时再换算回去。换算全程有理数（毫秒与 BPM 都按有理数处理），
   往返精确。**格式差异收敛在 codec 的映射表里，核心模型不动**
   ——这正是「换格式 = 换映射表」原则在时间域上的兑现。
5. **结论：不需要「灵活的多模式位置结构体」**。一个规范坐标
   (measure, Rational pos) + 一个 TimingEngine 接口就够。若将来出现
   真正无法表达为 (小节, 拍位置) 的格式（完全自由时间轴），
   需要扩展的只有 `Event<T>.pos` 一个坐标类型 + TimingEngine 一个缝，
   设计上已隔离到最小面。

### 2.3 ch02 与「拍子」惯例（补充确认）

- ch02 = **每小节拍数**（4/4 = 4，可小数如 2.5）；小节时长 = 拍数 × 60/BPM；
- 拍 = 四分音符、16 分音符只是槽位粒度（`Rational(i, N)` 的分母），
  这些对应关系**不存在于谱面文本**，只存在于换算逻辑里（2.2 的 TimingEngine）；
- 谱师手写惯例（默认 4/4）与模型默认值一致，无需额外建模。

## 3. 命令 JSON 协议规范（正式规格，M1 落地）

### 3.1 传输

`beatbench-cli --json '<请求>'`（内联）或 `beatbench-cli --json < req.json`（stdin）。
内容 UTF-8。每调用一个请求一个响应。

### 3.2 请求/响应信封

```
请求  { "id"?: 任意, "command": "名称", "args"?: 对象 }
成功  { "id"?, "ok": true,  "result": 任意 }
失败  { "id"?, "ok": false, "error": { "code": "稳定码", "message": "中文描述" } }
```

- `id` 可选，原样回显（便于批处理关联请求/响应）；
- `args` 缺省 = 空对象；`command` 必须为字符串；
- **dispatch 自身不抛异常**：信封/参数/命令错误全部收编为 `ok:false` 响应。

### 3.3 错误码表（稳定，客户端按 code 分支，不按 message）

| code | 含义 |
|---|---|
| `unknown_command` | 命令名未注册 |
| `bad_request` | 信封结构非法 / args 类型不符 / 缺键 |
| `bad_args` | 参数语义错误（如未知编码值） |
| `unsupported_format` | format 参数不是已注册格式（按 CodecRegistry 查找） |
| `output_exists` | convert 输出已存在且未传 overwrite:true |
| `read_failed` | 读取存在错误级诊断，拒绝继续 |
| `write_failed` | 无法写入输出文件 |
| `internal` | 不可预期异常（CLI 层兜底） |

### 3.4 退出码约定（CLI --json）

- `0` = 已产出信封（命令语义**只看信封 ok 字段**）；
- `2` = 无法产出信封（请求 JSON 非法 / 空输入），stdout 上仍给一个
  `bad_request` 信封；
- `1` = 内部异常（不应发生）。

### 3.5 内建命令（M1 起步，M3 大幅扩充）

| `convert` | input, output, encoding?, overwrite?, format? | written / bytes / from_encoding / to_encoding / diagnostics |

| `clipboard.copy` | selection, session_id? | lines[]（BMS 数据行文本） |

**元数据 / 采样管理**：

| 命令 | args | result 要点 |
|---|---|---|
| `meta.list` | session_id? | meta 对象 |
| `meta.edit` | edits[{key,value}], session_id? | — |
| `meta.rawEdit` | lines, session_id? | — |

`encoding`：读取侧 `auto`（默认）/`utf8`/`sjis`；convert 的 `encoding` 兼作写出编码（不支持 auto）。
`format`：按 CodecRegistry 动态查找（当前 `"bms"`；省略 = 按扩展名推断）。
`mode`：游玩模式覆盖（如 `"dp"` / `"pms9k"`；省略 = 按 #PLAYER/扩展名推断）。
所有编辑命令支持可选 `session_id`（缺省 = 活动会话）。

示例：

```
$ beatbench-cli --json '{"id":1,"command":"info","args":{"path":"local/chart/x.bms"}}'
{"id":1,"ok":true,"result":{"path":"...","format":"bms","mode":"sp7k","meta":{"TITLE":"..."},...}}
```

### 3.6 与人类 CLI 的关系

人类子命令（info/check/convert/version）与 JSON 命令共用同一批 core 函数，
经 CodecRegistry 统一分派（格式 → Codec → read/write），只差在展示层。
两条入口行为一致，不存在第二套逻辑。
